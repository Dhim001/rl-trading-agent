# RL Trading Agent - Full Functional Overview

This document explains the functionality of the full project in plain language (no code), including backend modules, scripts, and every page in the dashboard.

---

## 1) What this project does

This project is an end-to-end reinforcement learning (RL) trading system. It can:

- download and cache stock market data,
- engineer technical indicators,
- train an RL model for trading decisions,
- backtest model performance,
- run paper trading loops using live market inputs,
- run hyperparameter tuning with Optuna,
- display all outcomes in an integrated Streamlit dashboard.

The system supports both:

- **single-stock mode** (one symbol), and
- **multi-stock mode** (multiple symbols with symbol-aware actions).

---

## 2) High-level architecture

The project has three major layers:

1. **Core trading engine (`src/rl_trading_agent`)**
   - data processing, environments, risk controls, training, evaluation, and shared workflow definitions.

2. **Execution scripts (`scripts`)**
   - command-style entry points for download, train, backtest, tune, paper trade, and dashboard launch.

3. **User interface (`ui_dashboard`)**
   - a Streamlit app with operational controls and analytics views for outputs generated by the core engine.

---

## 3) Core backend modules (`src/rl_trading_agent`)

### `config.py`
- Loads project configuration from YAML.
- Central source for runtime parameters (data range, env settings, risk settings, training/tuning settings).

### `data/fetcher.py`
- Handles market data retrieval and cache reads.
- Uses local CSV cache first, then fetches from yfinance when needed.
- Normalizes date index handling for consistency.

### `data/features.py`
- Adds technical features/indicators to OHLCV data.
- Defines feature columns used by environments and model training.
- Normalizes selected feature columns using calculated statistics.

### `data/panel.py`
- Builds multi-symbol aligned datasets.
- Ensures all symbols share overlapping date windows.
- Produces normalized per-symbol frames and associated stats.

### `data/pipeline.py`
- Main data pipeline orchestration.
- Decides single vs multi-stock flow.
- Produces dataset + feature statistics + mode metadata.
- Includes helper logic for preparing normalized live data panels for paper trading.

### `env/trading_env.py`
- Single-stock Gymnasium environment.
- Defines observation state, action effects, reward, position accounting, and termination logic.

### `env/multi_stock_env.py`
- Multi-asset environment with symbol index + trade action behavior.
- Combines per-symbol features with portfolio state into model observations.
- Maintains multi-symbol holdings and equity dynamics.

### `env/factory.py`
- Unified environment factory.
- Creates either single-stock or multi-stock environment based on mode.
- Applies shared env/risk configuration.

### `risk/manager.py`
- Encapsulates risk constraints:
  - max drawdown rules,
  - stop-loss checks,
  - position sizing limits.
- Used by environments to enforce risk-aware actions and penalties.

### `training/trainer.py`
- Train/test splitting logic.
- Model construction for PPO/DQN.
- End-to-end training flow with callbacks (evaluation/checkpointing).
- Saves final trained model artifact.

### `training/tuner.py`
- Optuna-based search workflow.
- Varies learning rate, gamma, batch size, and window size.
- Runs training + backtest for each trial and optimizes Sharpe.
- Saves best hyperparameters.

### `evaluation/metrics.py`
- Computes backtest summary metrics:
  - total return,
  - Sharpe ratio,
  - max drawdown,
  - final equity.
- Saves equity curves to CSV.

### `evaluation/backtest.py`
- Loads a trained model and runs it through test data environment.
- Produces equity curve and summary metrics.
- Writes output artifacts for analysis.

### `dashboard/workflows.py`
- Shared workflow contract for UI and operations:
  - workflow IDs,
  - labels,
  - script command mappings.
- Reduces duplication between backend and dashboard layers.

### `dashboard/__init__.py`, `data/__init__.py`, `__init__.py`
- Package export and namespace wiring.

## 4) Script entry points (`scripts`)

### `download_data.py`
- Runs data pipeline download and preprocessing stage.
- Saves reusable feature stats and cache files.

### `train.py`
- Main training entry point.
- Loads config/data, splits datasets, trains model, and stores model outputs.

### `backtest.py`
- Runs model evaluation on held-out data.
- Outputs key performance metrics and equity curve file.

### `tune.py`
- Runs hyperparameter optimization via Optuna.
- Produces trial outputs and best-parameter summary.

### `paper_trade.py`
- Starts one-shot or looped paper trading process.
- Uses trained model and current market inputs to simulate decisions.

### `dashboard.py`
- Launches the integrated Streamlit dashboard from project root.
- Supports port/headless options.

## 5) UI Dashboard architecture (`ui_dashboard`)

### `app.py` (main dashboard shell)
- Dashboard app entry.
- Initializes config/state/services.
- Renders sidebar controls and page navigation.
- Lazily loads route page modules.
- Controls optional auto-refresh behavior.

### `core/config.py`
- Dashboard runtime config object:
  - project root,
  - runtime storage paths,
  - optional API base URL.

### `core/state.py`
- Session-state defaults for refresh, selected page, and operation mode.

### `core/types.py`
- Typed job record model used for local job tracking and persistence.

### `services/data_service.py`
- Data loaders and summary helpers used across pages:
  - JSON/JSONL/equity loaders,
  - tuning trial discovery,
  - equity summarization,
  - file age and size formatting.

### `services/job_service.py`
- Core operations service for launching and monitoring workflows.
- Supports:
  - local process execution mode,
  - optional remote API mode.
- Persists local job metadata and log files.
- Exposes launch/list/stop/log-tail methods.

### `services/api_adapter.py`
- HTTP adapter for external backend integration (if configured).
- Defines remote job endpoints:
  - create job,
  - list jobs,
  - stop job,
  - fetch log tail.

### `components/ui.py`
- Shared UI primitives for consistency:
  - freshness badges,
  - empty-state rendering,
  - error-state rendering.

## 6) Dashboard pages (`ui_dashboard/pages`)

### `overview_page.py`
- High-level summary metrics:
  - model count,
  - run folder count,
  - tuning trial count,
  - current paper cash.
- Shows latest backtest snapshot and freshness indicators.

### `backtest_page.py`
- Loads and charts backtest equity curve.
- Displays return/drawdown/final equity KPIs.
- Handles empty-state guidance if backtest artifacts are missing.

### `tuning_page.py`
- Displays best tuning parameters.
- Lists trial summaries and trial return chart.
- Allows selecting a trial to inspect its equity curve.

### `paper_page.py`
- Shows current portfolio state from paper trading.
- Plots paper trading equity-over-time.
- Displays recent paper-trade records from logs.

### `operations_hub_page.py`
- Operations control center for human users.
- Buttons to launch:
  - data download,
  - training,
  - backtest,
  - fine-tuning,
  - one-shot paper trade,
  - paper trading loop.
- Supports foreground/background run modes.
- Shows job table, stop control, and live log tail.

### `artifacts_page.py`
- Lists generated artifact files across models/runs/tuning/results/paper.
- Shows file size and modification timestamp.

### `pages/__init__.py`
- Page package namespace initialization.

## 7) Runtime outputs and data linkage

The dashboard and scripts are linked through file-based outputs and optional job APIs.

Key output artifacts:

- `models/final_model.zip` (trained model)
- `results/equity_curve.csv` (backtest output)
- `tuning/best_params.json` and `tuning/trial_*/results/equity_curve.csv` (tuning results)
- `paper/portfolio_state.json` and `paper/trades.log` (paper-trading state/log)
- `data/cache/*` and `data/feature_stats.json` (data layer outputs)

Dashboard local runtime metadata:

- `ui_dashboard/.runtime/jobs.json`
- `ui_dashboard/.runtime/jobs/*.log`

## 8) Operational flow summary

Typical lifecycle:

1. Download/prep data
2. Train model
3. Backtest model
4. Optional fine-tuning
5. Start paper trading
6. Monitor everything from dashboard pages and Operations Hub

---

## 9) Notes on integration and efficiency

- Workflow definitions are centralized in backend (`src/rl_trading_agent/dashboard/workflows.py`) and reused by UI services.
- Dashboard launcher is integrated into main scripts (`scripts/dashboard.py`).
- `scripts/run.ps1` provides single-command operational shortcuts.
- VS Code tasks map directly to common workflows.
